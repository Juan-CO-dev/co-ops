## The `resolvePar` zero-diff proof

**Claim: for every input reachable in production, the par this branch resolves is identical to `origin/main`'s — before 0183 is applied AND after.**

`origin/main` resolved `overlay?.field ?? global.field` per field, then the weekend day rule. This branch resolves `human ?? auto ?? global` per field, then the same day rule, unchanged and in the same place.

**Pre-apply — the auto fields are ABSENT, not null.** The four `auto*` fields are **optional** on `LocationSkuOverlay`, and the two loaders that build overlay objects (`loadOverlayBySku` in `lib/ordering.ts`, `loadParOverlay` in `lib/dynamic-pars.ts`) choose their select list from `parAutoLaneReady`. While that probe is false the select string is character-for-character the one on `main` (`"sku_id, active_override, weekday_par, weekend_par"`), and the assembled object has no `auto*` keys at all. `resolveLane` then reads `undefined` for `auto`, its `auto != null` test fails, and it returns `{ value: global }` — literally `overlay?.field ?? global.field`. **No new query is issued against a column that does not exist; the probe's own `select(...).limit(1)` is the only pre-apply cost, and it is the shipped 0180 pattern.**

**Post-apply — the columns exist and are all NULL.** `auto != null` is still false, so the same branch is taken. That holds not by luck but because **nothing in this branch can write a non-null auto value**, and there are exactly three writers:
1. `writeParFromSuggestion({ actorKind: "machine" })` — refuses twice, independently: `PAR_AUTO_APPLY_ENABLED` is false → `503`, and the probe is separately checked → `503`.
2. `upsertLocationSkuSettings` (the admin overlay editor) — resolves through `parWriteColumns({ kind: "admin" })`, whose auto-lane values are **NULL for every input** (asserted over every kind × day-class × value in `tests/dynamic-pars-write.test.ts`).
3. `writeParFromSuggestion({ actorKind: "accept" | "revert" })` — same pure authority, also all-NULL on the auto lane (a human write invalidates the machine's standing opinion by definition).

So post-apply the auto lane is provably all-NULL, and post-apply verification query ② above turns that proof into a live check.

**The two changed call sites.** `lib/ordering.ts:800` and `:1324` previously copied the overlay down to two fields before calling `resolvePar`. That copy predates the third lane and would have silently stripped it, making the machine lane unreachable from the only surface that renders pars — so both now pass `overlayRow` whole. Pre-apply `overlayRow` **has** only those two par fields plus `activeOverride` (which `resolvePar` ignores), so the copy and the original are the same object by value. `parIsWeekend` moved from `overlayForPar?.weekendPar ?? num(s.weekend_par)` to `resolveParSlot(...,"weekend").value`, which is the identical expression pre-apply and the correct one post-apply.

**Test evidence.** All 43 pre-existing `location-sku-shared` cases pass unmodified — they call `resolvePar` with two-field overlays, i.e. exactly the pre-apply shape. Three new cases assert the day-one and pre-apply equalities directly, and one asserts `resolvePar(x) === resolveParWithLane(x).par` across four overlay shapes × both day flags.

## Deviations, argued

**V1 — the probes live in a leaf module, `lib/dynamic-pars-probes.ts`, and are re-exported from `lib/dynamic-pars.ts`.** Task 3.9 puts them in `lib/dynamic-pars.ts`, and every consumer the plan names still imports them from there. They are *defined* one module down because two consumers sit **upstream** of the engine in the import graph — `lib/ordering.ts` (Task 3.3's select-list gate) and `lib/catering/toast-sales.ts` (Task 3.4) — and `lib/dynamic-pars.ts` imports both. Hosting the probes in the engine would make three pairs of modules mutually recursive for one boolean. This is the `*-shared.ts` re-export idiom AGENTS.md already codifies.

**V2 — `upsertLocationSkuSettings` routes through the authority's COLUMN half, not its async writer.** Task 3.8 says "rewire … to call it per changed slot". It calls `parWriteColumns({ kind: "admin", … })` — the same pure function `writeParFromSuggestion` resolves *its* columns through — and merges the result into its existing single upsert. Reason: that function owns a row the walker lanes do not. It writes `active_override` **and** both par slots together and must decide insert-vs-update, so delegating to a per-slot async writer would mean up to three UPDATEs racing on one row and three `vendor_item.update` audit rows for one operator edit. **The property r3 actually asks for is held exactly**: one place decides what a par write does to the machine lane, the baseline and the pin, and that place is `parWriteColumns`. Consequently `ParWriteInput.actorKind` is `Exclude<ParWriteActorKind, "admin">` — the server function does not carry a branch nothing reaches, while the pure table still covers all four kinds and is tested on all four.

**V3 — "directly edited" means the value CHANGED.** r3: "only a DIRECT human par edit at the same (SKU, location, slot) clears a PIN." The admin form resubmits both slots on every save, so clearing both pins on every save would let a weekday edit silently un-pin a weekend veto. `upsertLocationSkuSettings` now reads the existing `weekday_par`/`weekend_par` and treats a slot as edited only when its value differs. A resubmit of the same number is not an edit.

**V4 — `PAR_WRITE_MIN` is declared in the pure core, not imported from `lib/admin/skus.ts`.** Task 3.8 says "imported from `SKU_WRITE_MIN`, never re-declared, so the two can never drift". Importing it would create the V2 cycle in the other direction (`skus.ts` → `dynamic-pars.ts` → `skus.ts`) with a **top-level** const in TDZ, and `lib/admin/skus.ts` is server-only so no vitest case could reach the constant to check it. The drift guard is therefore made *real instead of nominal*: `tests/dynamic-pars-write.test.ts` asserts `PAR_WRITE_MIN === getRoleLevel("gm")` and that it is strictly above every level-6 role — which pins D1's actual claim (the floor is GM, and level 6 is where `social_media_mgr` lives) rather than pinning one number to another number.

**V5 — the reason ladder does NOT short-circuit on `slot_creation`.** Task 3.6's skeleton short-circuits on all of `SILENCING_REASONS`, which includes `slot_creation`. But **D16** requires the weekend day-class to be "always computed and always ledgered with `slot_creation = true`" so the aggregate can say "N SKUs look like they want a separate weekend par" — and Phase 2's merged `applyGuardStack` already carries a slot-creation branch that produces exactly that number. Short-circuiting would make that branch dead code and blind the aggregate to its own subject. `slot_creation` remains silencing on the *walker* (never a row-level number, D16) — it just is not a reason to stop computing. All other silencing reasons short-circuit as written.

**V6 — a null `computeCoverage` is attributed to its actual cause, not to `no_weight_basis`.** Task 3.6's skeleton writes `advisoryNullRow("no_weight_basis")` when coverage is null. By that point the ladder has already proven `perOrderUnitOz` is non-null, so the only remaining way `computeCoverage` returns null is a covered day whose **day-class has no rate** — which is thin history in the *other* day-class, not a missing weight. Sending Juan to the scale for a SKU that has been weighed is exactly the wrong errand, and LEAD RULING F3 already ruled this class of question ("the ledger's reasons are read as errands, so a wrong cause is a wrong errand"). The code keeps the `no_weight_basis` branch for the unreachable case rather than deleting it.

**V7 — `recordParRunSkipped` writes advisory-null LEDGER ROWS, not just an audit row.** Task 3.7 calls it and Task 3.6 lists it as orchestration, without saying what it persists. Writing only an audit row would leave last night's suggestions standing as the walker's latest ledger row for that location — which is precisely the "stale-computed" read r3 forbids ("materialize-failed locations get advisory-null, never stale-computed"). So it writes one `stale_depletion` row per (SKU, day-class) off **one** cheap SKU-list read: no demand loading, no rhythm, no product index.

**V8 — one read serves both the hysteresis prior and the budget.** The plan numbers them 11 and 12. Both want recent `par_auto_moves` rows at one location; two reads of one window would be two round trips for one fact. A 14-day window covers the prior; the budget filters to 7 inside it. (A 14th read was **added** — `par_suggestion_actions` — because reverts consume the budget per r2-8 and they are recorded as human actions, not ledger rows, so the budget's other half is not in `par_auto_moves` at all.)

**V9 — `derivePriorAndBudget` / `rollupPerDate` / `tallyRun` / `directionConfirmed` moved to a pure module.** `lib/dynamic-pars.ts` carries `import "server-only"`, so nothing inside it is reachable from vitest, and AGENTS.md requires that "new mixed modules should separate pure math so it CAN be tested". These four are the engine's silent-regression surface — especially the two exclusions the nightly job's idempotence rests on. `lib/dynamic-pars-run-shared.ts` + 27 cases. The engine keeps the I/O and the order.

**V10 — cosmetic: the Dynamic Pars block in `DESTRUCTIVE_ACTIONS` sits after the 2026-08-21 sweep blocks**, not immediately after "Product identity" as the task's prose says, so the product-identity quartet and its weight/basis riders stay one contiguous narrative.

**V11 — `RECIPE_EDIT_ACTIONS` is four names, not two.** The plan says "`recipe_input.*` / `recipe.update`"; live, `recipe_input.*` is three spellings (`add` + `remove` in `DESTRUCTIVE_ACTIONS`, `update` in `NON_DESTRUCTIVE_ACTIONS`) and all three change the flatten. Verified against both registries rather than assumed — an action name that does not exist would not error, it would silently never match, and the velocity reset would quietly stop working. Typed `satisfies ReadonlyArray<AuditAction>` so a rename breaks the build.
