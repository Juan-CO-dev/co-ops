## THE LAW

### Database & RLS

- **Never `FOR ALL` for write policies.** Permissive policies OR-stack per operation; `FOR ALL` silently permits DELETE. Always split `FOR INSERT` + `FOR UPDATE`, paired with explicit `FOR DELETE USING (false)`.
- **RLS helper functions are `SECURITY DEFINER` with `SET search_path = pg_catalog, public`** — else self-referencing policies recurse to stack-death. `REVOKE FROM PUBLIC` is NOT enough on Supabase: default ACLs grant EXECUTE to `anon` explicitly — revoke from `anon` too and verify via `information_schema.routine_privileges`.
- **UPDATE denials are silent** (`UPDATE 0`, no error; INSERT denials raise 42501). Every UPDATE route must check rowcount and return an explicit 403/404.
- **Append-only is law, enforced at RLS** (`_no_user_delete USING (false)` everywhere). Config rows deactivate via `active = false`; history is sacred. If you want to DELETE, you're in the wrong code path — flip active, append a correction, or supersede.
- **Policy naming:** `<table>_<action>` for allows, `<table>_no_user_<operation>` for explicit denies.
- **Column-level enforcement is app-layer** (Postgres can't do per-column RLS): documented sites include `shift_overlays.forecast_notes` (CGS-only), vendors trivial-vs-full edit split, notification-recipient fields, users self-update fields. `canActOn` (admin acts only on strictly-lower level) is app-layer too — `lib/roles.ts`.
- **Pre-flight every SQL emission against the live schema:** `information_schema.columns` before any INSERT into a shared table (never infer columns from JS helpers — they pack richer args than tables store); `pg_enum` before any INSERT into an enum column (design-doc shorthand ≠ production labels).
- **Every migration applied via MCP also lands as `supabase/migrations/NNNN_<name>.sql` in the same PR** (provenance header + original comment block; see PHASE_HISTORY for the two header formats). Migration-driven audit rows use `metadata.actor_context = "migration_apply"` and set `destructive` explicitly.
- **Template evolution:** in-place additive ONLY when all changes are additive inserts or label-only updates preserving `template_item.id`; anything structural (removals, role-level changes, semantic renames) = Path A versioning (ship vN+1 active, validate, flip vN inactive in a follow-up, document stranded instances in the audit metadata).
- Supabase JS `.update()` **swallows constraint violations** — always check `error`, never infer success from `data`.
- Postgres temp tables aren't shared across `SET ROLE` switches — grant or create after switching.
- PostgREST v12+ reads claims from `request.jwt.claims` (plural JSONB) only; embedded-select `.eq()` filters on relations are fragile under RLS — prefer two-step queries.

### Auth & sessions

- **JWT claim shape (locked):** `{ user_id, app_role, role_level, locations, session_id, role: 'authenticated' }`. `role` is PostgREST's database role — the app role lives in `app_role`, always.
- **`AUTH_JWT_SECRET` is hex-interpreted** (`Buffer.from(secret, "hex")`) — Supabase hex-decodes HS256 secrets on key creation. Rotating the app secret without the Supabase standby key (or vice versa) 500s every request — see `docs/runbooks/jwt-rotation.md`.
- **Dual verification:** JWT signature AND `sessions.token_hash` (SHA-256 of the raw JWT). Mismatch = audited `session_token_mismatch` + 401 + cleared cookie.
- **JWT-embedded authz claims have refresh latency** → any admin mutation affecting authorization (deactivate, role change, location change, credential change) MUST revoke the target's active sessions in the same transaction (`revokeAllUserSessions`, shipped PR #79). `revokeSession` is idempotent; callers interpret `rowsAffected: 0` per context.
- **PINs are 4 digits for ALL roles** (Toast/7shifts parity — locked). Lockout: 5 failures / 15-min. **Defensive `missing_*_hash` branches are countable failures** (else no-hash accounts are un-lockable), and the lockout check runs on the threshold-crossing attempt (no off-by-one 401).
- **Lowercase every email at insert time** — lookups lowercase, the column is case-sensitive, and `email_not_found` is (deliberately) not countable, so a mixed-case insert = permanently unloginable with no user-visible diagnostic.
- Constant-shape responses on enumeration surfaces (`verify`, `password-reset-request`); internal disposition goes in audit metadata only. `/api/users/login-options` is a documented, accepted enumeration tradeoff (tile login UX).
- Proxy 307s preserve method — UI treats 307 from API routes as auth failure; test fetches use `redirect: "manual"`.
- `requireSessionFromHeaders` = Server Component variant (redirects); `requireSession` = route variant (returns 401). `lib/session.ts` is Node-runtime only; `proxy.ts` (edge) imports from `lib/auth.ts` only.

### Audit & append-only conventions

- One `audit()` helper (`lib/audit.ts`), service-role-only, **fail-open** (logging failure never breaks the flow). `destructive` auto-derives from the `DESTRUCTIVE_ACTIONS` registry.
- **Vocabulary:** lifecycle = dot-namespaced (`user.create`, `checklist_template.delete_or_deactivate`); auth events = flat `auth_*` namespace (locked list in PHASE_HISTORY). Never invent parallel action names.
- **`audit.gap_recovery`** = new row covering changes that landed without their audit row (op-by-op `orphaned_changes` + `resolving_audit_row_id`). **`audit.metadata_correction`** = corrects a prior row's metadata. Never UPDATE audit rows — corrective rows are the only path. Orphaned `resource_id`s in audit_log are valid forensic evidence, not bugs.
- Seed scripts: hardcoded `phase`/`reason` metadata MUST be updated before any re-run in a new context; data-exporting seeds gate `main()` behind a `pathToFileURL(process.argv[1])` direct-invocation check (import side-effect re-runs are a real incident class).
- Self-updates that are routine preferences (language, phone) skip audit; anything security-relevant gets one.

### UI design system (token floor, 2026-08-19)

- **Four button grammars coexist and must NOT be collapsed.** `ActionButton` (operational: `rounded-xl`, 48/56px, primary border is **`border-co-text`** not gold-deep, `danger` is a red **OUTLINE** — never a red fill — and its edge *and* label both take **`co-cta-text`**, never `co-cta`) · admin-form (`rounded-lg`, 44px, `border-co-gold-deep`) · catering/portal (`rounded-xl`, ink fill, `tracking-[0.12em]`; the portal's own eyebrow/kicker labels — nav wordmark, section eyebrows, hero eyebrow — run a deliberately wider tracking scale, `0.16em`–`0.32em` across several distinct values, RATIFIED as this grammar's own label system, not drift off the two roles below) · auth-primary (`SetPasswordForm`/`ManagerLoginForm`/`PasswordModal`/`IdleTimeoutWarning`: `rounded-xl`, `min-h-[52px]`, ink fill `bg-co-text`, label `text-co-cta`, `tracking-[0.12em]` — contrast-compliant because the ground is dark, same idea as catering/portal, ratified 2026-08-20). A surface adopts one grammar whole; mixing spellings is the drift `ActionButton` was written to end.
- **Two label roles, and they are not interchangeable.** Group header = 12px / 700 / `tracking-wide` (**0.025em**) / `text-co-text-muted`. Field-or-sub label = 10–11px / 700 / `tracking-[0.12em]` / `text-co-text-dim`. **0.14em is reserved for section headers**; 0.08em is the small-control label. Converting `tracking-wide` to a loose value collapses the two roles into one. (The portal's own eyebrow tracking scale is a separate, ratified grammar — see above — not a violation of this pair.) **`tracking-[0.1em]` is the BUTTON-label value** — ActionButton's own spelling, and the admin-form grammar's control labels share it (ratified 2026-08-20, 53-of-60 live consistency; it belongs to controls, never to standalone labels).
- **44px control floor, ALWAYS paired with `items-center`** — a 44px control without centring does not exist upstream. A control sized only by padding still needs the floor; an absent height is a value, not an exemption. An element declaring both width and height is an icon button: **size both axes or neither**, or a `rounded-full` button becomes an ellipse. Never let a border condition split a control group (a stepper's `+` and `−` size as one unit). Checkboxes keep a 20px box inside a 44px **label** hit area.
- **Token roles are the law; the name tells you what it is for.** `co-border` = panels/inputs · `co-border-2` = control emphasis · `co-card-border` = the `.co-card` hairline **ONLY, and never a utility** (it has no `@theme` entry on purpose; `border-co-card-border` silently emits nothing and the edge renders ink) · `co-gold-text` = gold TEXT on light grounds · `co-gold-deep` = pressed/border/fill, **never** light-ground text · `co-cta` = red **fills**, and the edge of a filled red control · `co-cta-text` = red **TEXT** on light grounds **and the edge of a red outline on a light fill** (`co-cta` falls to 2.94:1 against the hover tint, under the 3:1 non-text floor — so a danger outline's edge and label move together) · destructive fill = **ink on cta**, never white or cream on cta · **every status color splits fill from text the same way**: `co-warning` / `co-success` / `co-danger` are **fills, dots and borders ONLY** (as text on their own pale surfaces they measure 1.95:1 / 2.49:1 / 2.94:1), and their text roles are `co-warning-text` (#8A5700, 5.55:1 on warning-surface) · `co-confirm-text` (#14532D — **THE** dark-green text role, confirm affordances AND success/ok status text; there is deliberately **no `co-success-text`**, a second name for one role is the drift the floor prevents) · `co-cta-text` · `bg-co-gold/20` = the documented brand-badge tint spelling (role chips, brand accents ONLY; a status/warning surface uses `co-warning-surface`/`co-danger-surface` instead, a hover/pressed state uses `co-surface-2` — ratified 2026-08-20, no new token minted) · surface levels: `co-surface` (cards) / `co-surface-inset` (nested panels) / `co-surface-2` (hover-pressed only).
- **A new color utility needs BOTH halves of `app/globals.css`** — the raw var in `:root` AND the `--color-*` mapping in `@theme inline`. A missing `@theme` entry is a **silent no-op**, not an error. `scripts/check-ui-tokens.ts` catches the class; it is manual-run, not gated.
- **Contrast is computed against the COMPOSITED background, not the declared one.** The page ground is `--co-bg` **plus** the `body` gradient `linear-gradient(170deg, #FFFDF5, #FFF3D4)`; composite front-to-back (`acc += a*(1-acc)`) starting at the element's own background, and read `backgroundImage` or a gradient band resolves to transparent. The difference is ~0.45 of a ratio point and it decides AA calls.
- **Authority:** the full design reference is `docs/design/2026-08-19-ux-refresh-handoff/`. Its **README's reconciled table is spec**; the per-turn annotations in `github.md` are working notes and are **NOT authoritative**. The repo still wins over both on structure, routing, gating, and naming.

### Product identity (0179–0181, arc closed 2026-08-21)

- **FOUR LAYERS, one pointer changed.** `menu_items` → `items` (prep registry) → **`products`** → `vendor_items` (per-vendor packs, prices, weights, pars). A product is the raw identity a recipe means ("HAM"); member SKUs attach via `vendor_items.product_id`. **A SKU with `product_id` NULL is an implicit SINGLETON** — resolution is trivially itself — which is why ~95% of the catalog has no product row and needed no data migration. Products exist only where PLURALITY does. Retirement is `active = false`; append-only, no DELETE path.
- **RESOLUTION HAPPENS ONCE, AT GRAPH BUILD, AND IT IS PURE.** `resolveProductMember` (`lib/products-shared.ts`) is THE ladder: **⓪ the PRODUCT itself is retired → honest `unresolved`** ① the primary flagged for this location, **if active** ② else the most-recently-**received** active member ③ else any active member (`skuId` ascending — a stable, not arbitrary, pick) ④ else honest `unresolved`. A flagged primary that is inactive or not a member **falls through; it never fails the product** — that is the vendor-down behavior the whole layer exists for. `loadRecipeGraph` runs it and hands every consumer a resolved SKU id, so costing, depletion, production, counts and ordering stay SKU-keyed and gain failover for free. **Never resolve a product a second time in a consumer** — a second resolver is a second opinion about which vendor a product means, which is exactly what this layer was built to end. `product_primaries` uses the `location_id NULL = global` house idiom, and membership is DB-proven by a composite FK, never app-trusted.
- **RETIREMENT REFUSES, AND THE RECIPE GOES LOUD** (Juan's ruling A+, 2026-08-21; sim P1-9). `products.active = false` is Juan declaring a fact about the kitchen — we do not buy this identity any more — and rung ⓪ honours it ahead of every member check, because a retired product's members are normally still active rows and falling through would overrule the declaration with an inference. `ProductResolution.reason` names the cause (`retired_product` vs `no_active_member`): the STATUS stays the single `unresolved` everywhere downstream — costing board, depletion, production, ordering — but the drawer, the readiness lane and the audit row say WHICH errand fixes it: a recipe edit, not a trip to the SKU catalog. **RECIPE EDITING ≠ RETIREMENT.** Swapping a product out of one recipe is just recipe editing and touches none of this. **Retirement means "we stop buying this entirely", which is an ORDERING-layer decision** (Juan, 2026-08-21) — so **the par pass SUPPRESSES par'd member SKUs of a retired product**: they drop from suggestions, they are never rescued by the vendor-down failover (rescuing would re-order the product we stopped buying), and they surface in the walk's warn lane as `productRetired` ("discontinued — par suppressed"), loud and never silent. **Pars are SUPPRESSED, never MUTATED** — the `weekday_par`/`weekend_par` columns are untouched, so bringing the product back restores the exact prior walk with no par re-entry. Pars are downstream of demand (they exist *because* recipes create demand), so a retired product's pars are stale by definition.
- **PAR ADVISORIES ARE CAUSE-ATTRIBUTED, AND NEVER NUMERIC** (Juan, 2026-08-21: *"the pars should be loud about why they need to be tuned down when demand lessens… the system recognizes what's going on before the human does"*). `parReviewAdvisory` (`lib/location-sku-shared.ts`) nudges a par only on a **CHANGE** — a discontinued product, or a recipe that stopped using the SKU — and it NAMES the recipe. **A STATE IS NEVER A TRIGGER:** "has no active recipe" fires nothing, because live-verified 2026-08-21 that state covers 57 inventory-only SKUs plus 16 resale goods (Coke, Saratoga, Frooties…) that correctly have no recipe — an advisory on it would cry wolf on ~73 of its first 77 rows, and a lane that cries wolf gets scrolled past. **Suggesting a par NUMBER is out of scope and reserved for the Dynamic Pars arc**: that needs demand-rate math over a velocity window, and a figure invented from one removed recipe line would be exactly the confident-number-with-nothing-behind-it the costing board's `unweighed` status exists to refuse. **`loadProductIndex` deliberately does NOT `.eq("active", true)` the products select**: a filtered-away row poisons with no name, and `productBySku` + the member list are still true facts a count sheet uses to label twins. The active filter lands *inside* the pure resolver, which is the only place that can name itself. Same historical-replay boundary #272 drew for inactive recipes: nothing replays history through this loader, and ledger rows keyed by `vendor_items.id` are never re-resolved. **Retiring NEVER hard-blocks** — `/admin/products` warns "N recipes still pin this" (named when few) and proceeds; the write-time guard (`assertProductLineIsValid`) only stops a NEW line being authored into that state. Readiness gains two codes: `retired_product` (RED, a real refusal) and `retired_sku` (AMBER RIDER — a deactivated SKU pin gets **loudness only**, because `loadSkuPack` still includes inactive SKUs for historical replay and flipping that moves live numbers; it is its own decision).
- **A PRODUCT OWNS `unit_oz`, NOT A PACK.** A product-pinned recipe line may be denominated ONLY in a **measure-registry** unit; `productInputBasis` returns `packChain`/`packFormat`/`eachContainerLabel` all null so `ozForRecipeInput` lands on the registry. "1 case" of one vendor's ham is not "1 case" of another's, and a product pin has no honest way to choose — so it is not offered the choice. A count-denominated line resolves through `products.unit_oz`, member-independent by construction; that is what makes a member flip cost the same ounces. `addRecipeInput` rejects a pack-label unit at write time by name. NULL `unit_oz` refuses (poisons to `unresolved`) rather than guessing.
- **FIFO IS A READ-TIME ATTRIBUTION. The depletion ledgers are never re-keyed.** `toast_daily_depletion.direct_oz` keeps its exact meaning, `flattened_oz` is still never summed into drift, and **the double-count law is not in play here**. FIFO runs in the pure core over lots assembled from `vendor_delivery_items` (`created_at` is the lot instant), oldest-first with a `lotId` tiebreak; what a lot cannot explain is **reported as unattributed, never smeared and never dropped**. The mirrored false SHORT/OVER pair is cured by the **rollup** — twins net at product grain — not by touching a ledger row.
- **A PRODUCT-LEVEL COUNT WRITES ORDINARY PER-SKU LINES.** `sku_count_lines` gains no product grain; C-mode resolves oz through the primary's basis, allocates it across member lots **newest-back** (the freshest lots are what the counter is looking at), and writes one line per member with `allocated_from_product_id` set — NULL means counted directly. **Every active member gets a line, including a zero one:** a product count re-anchors the WHOLE product, and that zero is a *measured* zero ("none of it is Baldor's"), categorically different from the F3 refusal of an operator typing 0. **A COUNT IS GROUND TRUTH AND THEORY YIELDS TO IT** — oz the ledger cannot place is attributed to the resolved primary with an advisory reason code (`no_lot_history` when there are no lots at all; `count_exceeds_lots` when there are and they fall short — never conflate them), never refused. **One product line per event**: two lines for one product breaks the council-L5 disjointness the anchor sum rests on. On-hand is TWO GRAINS: the per-SKU ledgers stay the truth, the product grain is their sum, `totalOz` is non-null only when every member resolved, and `knownOz` is a lower bound that must never render where a total belongs.

### Engineering doctrine

- **Verify against operational artifacts, not generic priors.** CO has zero walk-ins and zero freezers; it has eight under-station fridges. The existing templates, paper checklists, schema, and Juan's floor knowledge are ground truth; training-data "what a restaurant has" is not. Multi-source verification (Juan's knowledge / DB queries / paper artifacts / code pre-read / rendered smoke) before locking operational structure — each source class catches gaps the others miss.
- **"Preserved from prior" must be re-verified against any amendment that changed its operational assumptions** (the C.54 §9 production wedge). When an amendment lands, audit every carried-forward branch for invalidated assumptions.
- **Before building a reader, confirm the writer runs in prod** — a correct-shaped consumer of a contract nobody produces is dead code that looks finished.
- **The codebase has usually already built the thing** — read for existing scaffolding/patterns before scoping anything as greenfield (three-plus confirmed repetitions).
- **Read surfaces over new workflows:** new capability defaults to a computed read over existing capture artifacts; new workflows only when the data genuinely doesn't exist — and then extend an existing artifact first.
- **Wire-shape coupling sets commit boundaries:** form/route/RPC/migration/type changes that are type-coupled ship together; splitting at conversational boundaries produces broken intermediate states.
- **Validation iterates the source of truth** (templateItems, schema, config), never operator-state-only structures (rawValues, dirty sets) — the latter are a subset.
- **Shared-type changes get a consumer grep before commit** (`grep -rE "<TypeName>\b"`); role-gate changes get the 3-layer sweep (lib + RLS + UI, both directions of the comparison).
- **Ship-complete:** partial scope must clear the architectural-deferral bar (different module/data model/tempo, deserving its own design). "Translate it later" and its cousins never clear the bar.
- **Smoke tests are architectural finders:** when a first-shift report feels off, surface the architectural read BEFORE bug-fixing. `router.refresh()` does NOT reset client `useState`; prop-driven client-state resets use the during-render prev-compare pattern, not effects; irreversible affordances gate on server-authoritative status, never spinner state. Map observed→expected before calling a smoke red — refusal-to-resubmit is the fix working.
- **Operational voice varies by audience:** capture surfaces use the actor's technical wording; notification/consume surfaces use operational shorthand; both registers survive translation.
