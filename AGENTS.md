## THE LAW

### Database & RLS

- **Never `FOR ALL` for write policies.** Permissive policies OR-stack per operation; `FOR ALL` silently permits DELETE. Always split `FOR INSERT` + `FOR UPDATE`, paired with explicit `FOR DELETE USING (false)`.
- **RLS helper functions are `SECURITY DEFINER` with `SET search_path = pg_catalog, public`** — else self-referencing policies recurse to stack-death. `REVOKE FROM PUBLIC` is NOT enough on Supabase: default ACLs grant EXECUTE to `anon` explicitly — revoke from `anon` too and verify via `information_schema.routine_privileges`.
- **UPDATE denials are silent** (`UPDATE 0`, no error; INSERT denials raise 42501). Every UPDATE route must check rowcount and return an explicit 403/404.
- **Append-only is law, enforced at RLS** (`_no_user_delete USING (false)` everywhere). Config rows deactivate via `active = false`; history is sacred. If you want to DELETE, you're in the wrong code path — flip active, append a correction, or supersede.
- **Policy naming:** `<table>_<action>` for allows, `<table>_no_user_<operation>` for explicit denies.
- **Column-level enforcement is app-layer** (Postgres can't do per-column RLS): documented sites include `shift_overlays.forecast_notes` (CGS-only), vendors trivial-vs-full edit split, notification-recipient fields, users self-update fields. `canActOn` (admin acts only on strictly-lower level) is app-layer too — `lib/roles.ts`.
- **Pre-flight every SQL emission against the live schema:** `information_schema.columns` before any INSERT into a shared table (never infer columns from JS helpers — they pack richer args than tables store); `pg_enum` before any INSERT into an enum column (design-doc shorthand ≠ production labels).
- **Every migration applied via MCP also lands as `supabase/migrations/NNNN_<name>.sql` in the same PR** (provenance header + original comment block; see PHASE_HISTORY for the two header formats). Migration-driven audit rows use `metadata.actor_context = "migration_apply"` and set `destructive` explicitly.
- **Template evolution:** in-place additive ONLY when all changes are additive inserts or label-only updates preserving `template_item.id`; anything structural (removals, role-level changes, semantic renames) = Path A versioning (ship vN+1 active, validate, flip vN inactive in a follow-up, document stranded instances in the audit metadata).
- Supabase JS `.update()` **swallows constraint violations** — always check `error`, never infer success from `data`.
- Postgres temp tables aren't shared across `SET ROLE` switches — grant or create after switching.
- PostgREST v12+ reads claims from `request.jwt.claims` (plural JSONB) only; embedded-select `.eq()` filters on relations are fragile under RLS — prefer two-step queries. **THE HAZARD IS RLS-SCOPED, and the law is bounded to it** (lead ruling, PR #285): under a user-context read, a filter on a relation the caller cannot fully see behaves unpredictably. On a **service-role** client, which bypasses RLS entirely, an embed is legitimate — and is sometimes the only correct answer, because the two-step alternative spends an unbounded id list in the GET request line (see `DELIVERY_AT_LOCATION_EMBED` in `lib/products.ts`: the id list was a 414 at ~220 deliveries, and the embed made the request line constant). Two conditions on a service-role embed: **disambiguate by FK constraint name** whenever more than one FK joins the two tables (`vendor_delivery_items` has two to `vendor_deliveries` — a bare `!inner` fails `PGRST201`), and **verify row-for-row parity against the query it replaces** before the swap. Do not re-litigate this; do not extend it to user-context reads.

### Auth & sessions

- **JWT claim shape (locked):** `{ user_id, app_role, role_level, locations, session_id, role: 'authenticated' }`. `role` is PostgREST's database role — the app role lives in `app_role`, always.
- **`AUTH_JWT_SECRET` is hex-interpreted** (`Buffer.from(secret, "hex")`) — Supabase hex-decodes HS256 secrets on key creation. Rotating the app secret without the Supabase standby key (or vice versa) 500s every request — see `docs/runbooks/jwt-rotation.md`.
- **Dual verification:** JWT signature AND `sessions.token_hash` (SHA-256 of the raw JWT). Mismatch = audited `session_token_mismatch` + 401 + cleared cookie.
- **JWT-embedded authz claims have refresh latency** → any admin mutation affecting authorization (deactivate, role change, location change, credential change) MUST revoke the target's active sessions in the same transaction (`revokeAllUserSessions`, shipped PR #79). `revokeSession` is idempotent; callers interpret `rowsAffected: 0` per context.
- **PINs are 4 digits for ALL roles** (Toast/7shifts parity — locked). Lockout: 5 failures / 15-min. **Defensive `missing_*_hash` branches are countable failures** (else no-hash accounts are un-lockable), and the lockout check runs on the threshold-crossing attempt (no off-by-one 401).
- **Lowercase every email at insert time** — lookups lowercase, the column is case-sensitive, and `email_not_found` is (deliberately) not countable, so a mixed-case insert = permanently unloginable with no user-visible diagnostic.
- Constant-shape responses on enumeration surfaces (`verify`, `password-reset-request`); internal disposition goes in audit metadata only. `/api/users/login-options` is a documented, accepted enumeration tradeoff (tile login UX).
- Proxy 307s preserve method — UI treats 307 from API routes as auth failure; test fetches use `redirect: "manual"`.
- `requireSessionFromHeaders` = Server Component variant (redirects); `requireSession` = route variant (returns 401). `lib/session.ts` is Node-runtime only; `proxy.ts` (edge) imports from `lib/auth.ts` only.

### Audit & append-only conventions

- One `audit()` helper (`lib/audit.ts`), service-role-only, **fail-open** (logging failure never breaks the flow). `destructive` auto-derives from the `DESTRUCTIVE_ACTIONS` registry.
- **Vocabulary:** lifecycle = dot-namespaced (`user.create`, `checklist_template.delete_or_deactivate`); auth events = flat `auth_*` namespace (locked list in PHASE_HISTORY). Never invent parallel action names.
- **THE ACTION VOCABULARY IS CLOSED, AND THE COMPILER ENFORCES IT** (2026-08-21). `AuditInput.action` is typed as `AuditAction` — the union of `lib/audit-actions.ts` — **never `string`**. Every action must be adjudicated into `DESTRUCTIVE_ACTIONS` (`lib/destructive-actions.ts`) or `NON_DESTRUCTIVE_ACTIONS`, with no silent third state; a new name that is in neither **fails the build at the call site**. While it was `string`, an unregistered action was indistinguishable from a deliberately-non-destructive one and defaulted quietly to `destructive=false` — which is how ten actions reached prod unregistered, three of them beside their own registered siblings. `RESERVED_ACTIONS` holds registry entries TypeScript never writes (`report.update` is emitted from SQL, where `isDestructive` is bypassed and the migration sets the column literally; the rest are unbuilt capability). **Grep-invisible call sites are the recurring hazard** — a template literal, or an action passed through a variable — so a helper that forwards an action types the parameter as `AuditAction`, never `string`.
- **What "destructive" MEANS, and what it does NOT do:** an action is destructive when a **human act** alters shared operational config or the accountability record — the filter for "who changed the kitchen?". A **system observation** is never destructive however consequential (`product.resolution_flip` is written by the nightly materialization with `actor_id` null). Membership does **NOT** gate step-up: `isDestructive` feeds exactly one thing, the `destructive` column, and step-up is enforced independently by route/path in `lib/admin/step-up.ts`. The registry header claimed otherwise for years and the stale claim caused a wrong call (the product-identity plan declined to register a family on step-up grounds this list does not control). Adding a name changes what is FINDABLE, never what is PERMITTED.
- **`audit.gap_recovery`** = new row covering changes that landed without their audit row (op-by-op `orphaned_changes` + `resolving_audit_row_id`). **`audit.metadata_correction`** = corrects a prior row's metadata. Never UPDATE audit rows — corrective rows are the only path. Orphaned `resource_id`s in audit_log are valid forensic evidence, not bugs.
- Seed scripts: hardcoded `phase`/`reason` metadata MUST be updated before any re-run in a new context; data-exporting seeds gate `main()` behind a `pathToFileURL(process.argv[1])` direct-invocation check (import side-effect re-runs are a real incident class).
- Self-updates that are routine preferences (language, phone) skip audit; anything security-relevant gets one.

### i18n

- **Translate-from-day-one:** every new UI surface ships en + es keys in the same PR. "Translation pass deferred" is scope-incomplete. One key per visible string AND every ARIA label. Spanish is operational tú-form, not formal.
- **System-key vs display-string (architectural rule):** any field that is both a match key and user-visible renders translated but MATCHES on the English original (canonical: the Walk-Out Verification gate). Never compare translated strings.
- **Language is NOT in the JWT** — read fresh from `users` per render (post-toggle staleness). Keep JWTs to authorization claims; user preferences read per-request.
- **All date/time formatting is language-aware via `lib/i18n/format.ts` helpers** (`formatTime`, `formatDateLabel`, `formatChainAttribution`) — never `toLocale*(undefined, …)`, never hardcoded locale, never new inline copies.
- Template-item content translates via `lib/i18n/content.ts` resolver (JSONB `translations`); admin editors for template content MUST expose Spanish fields alongside English (C.44) or they recreate the partial-translation gap.

### Build, CI & git discipline

- **CI gate:** the required `build` check runs discipline check + `npm test` + `next build` on every PR. `next build` is a SEPARATE gate from dev/typecheck (e.g. `useSearchParams()` needs `<Suspense>` only at build). Never merge red.
- **Any commit containing a code file goes through a PR + CI. Direct-push is for pure-docs commits only.** (A `.ts` smuggled into a docs push broke main once — the rule is blood-bought.)
- **Smoke against the PR's preview URL** (Vercel comment on the PR), never production — prod serves main, not your branch.
- Long sessions: **commit per step** (`wip(...)`) — a worktree wipe erased 5 hours once. Worktrees are filesystem-isolated: copy `.env.local` + untracked assets in.
- Squash-merge + same-branch series = `git fetch && git reset --hard origin/main` between PRs. Remote branch deletion: `gh api -X DELETE .../git/refs/heads/<branch>` (never `gh pr merge --delete-branch` from a worktree repo).
- If pushes stop triggering `pull_request` runs on a branch: close/reopen the PR (`reopened` is a default trigger). Verify env vars by pulling and checking value LENGTH (`vercel env ls` shows records, not whether they're empty); `NEXT_PUBLIC_*` inline at build — repopulate then rebuild without cache.

### UI design system (token floor, 2026-08-19)

- **Four button grammars coexist and must NOT be collapsed.** `ActionButton` (operational: `rounded-xl`, 48/56px, primary border is **`border-co-text`** not gold-deep, `danger` is a red **OUTLINE** — never a red fill — and its edge *and* label both take **`co-cta-text`**, never `co-cta`) · admin-form (`rounded-lg`, 44px, `border-co-gold-deep`) · catering/portal (`rounded-xl`, ink fill, `tracking-[0.12em]`; the portal's own eyebrow/kicker labels — nav wordmark, section eyebrows, hero eyebrow — run a deliberately wider tracking scale, `0.16em`–`0.32em` across several distinct values, RATIFIED as this grammar's own label system, not drift off the two roles below) · auth-primary (`SetPasswordForm`/`ManagerLoginForm`/`PasswordModal`/`IdleTimeoutWarning`: `rounded-xl`, `min-h-[52px]`, ink fill `bg-co-text`, label `text-co-cta`, `tracking-[0.12em]` — contrast-compliant because the ground is dark, same idea as catering/portal, ratified 2026-08-20). A surface adopts one grammar whole; mixing spellings is the drift `ActionButton` was written to end.
- **Two label roles, and they are not interchangeable.** Group header = 12px / 700 / `tracking-wide` (**0.025em**) / `text-co-text-muted`. Field-or-sub label = 10–11px / 700 / `tracking-[0.12em]` / `text-co-text-dim`. **0.14em is reserved for section headers**; 0.08em is the small-control label. Converting `tracking-wide` to a loose value collapses the two roles into one. (The portal's own eyebrow tracking scale is a separate, ratified grammar — see above — not a violation of this pair.) **`tracking-[0.1em]` is the BUTTON-label value** — ActionButton's own spelling, and the admin-form grammar's control labels share it (ratified 2026-08-20, 53-of-60 live consistency; it belongs to controls, never to standalone labels).
- **44px control floor, ALWAYS paired with `items-center`** — a 44px control without centring does not exist upstream. A control sized only by padding still needs the floor; an absent height is a value, not an exemption. An element declaring both width and height is an icon button: **size both axes or neither**, or a `rounded-full` button becomes an ellipse. Never let a border condition split a control group (a stepper's `+` and `−` size as one unit). Checkboxes keep a 20px box inside a 44px **label** hit area.
- **Token roles are the law; the name tells you what it is for.** `co-border` = panels/inputs · `co-border-2` = control emphasis · `co-card-border` = the `.co-card` hairline **ONLY, and never a utility** (it has no `@theme` entry on purpose; `border-co-card-border` silently emits nothing and the edge renders ink) · `co-gold-text` = gold TEXT on light grounds · `co-gold-deep` = pressed/border/fill, **never** light-ground text · `co-cta` = red **fills**, and the edge of a filled red control · `co-cta-text` = red **TEXT** on light grounds **and the edge of a red outline on a light fill** (`co-cta` falls to 2.94:1 against the hover tint, under the 3:1 non-text floor — so a danger outline's edge and label move together) · destructive fill = **ink on cta**, never white or cream on cta · **every status color splits fill from text the same way**: `co-warning` / `co-success` / `co-danger` are **fills, dots and borders ONLY** (as text on their own pale surfaces they measure 1.95:1 / 2.49:1 / 2.94:1), and their text roles are `co-warning-text` (#8A5700, 5.55:1 on warning-surface) · `co-confirm-text` (#14532D — **THE** dark-green text role, confirm affordances AND success/ok status text; there is deliberately **no `co-success-text`**, a second name for one role is the drift the floor prevents) · `co-cta-text` · `bg-co-gold/20` = the documented brand-badge tint spelling (role chips, brand accents ONLY; a status/warning surface uses `co-warning-surface`/`co-danger-surface` instead, a hover/pressed state uses `co-surface-2` — ratified 2026-08-20, no new token minted) · surface levels: `co-surface` (cards) / `co-surface-inset` (nested panels) / `co-surface-2` (hover-pressed only).
- **A new color utility needs BOTH halves of `app/globals.css`** — the raw var in `:root` AND the `--color-*` mapping in `@theme inline`. A missing `@theme` entry is a **silent no-op**, not an error. `scripts/check-ui-tokens.ts` catches the class; it is manual-run, not gated.
- **Contrast is computed against the COMPOSITED background, not the declared one.** The page ground is `--co-bg` **plus** the `body` gradient `linear-gradient(170deg, #FFFDF5, #FFF3D4)`; composite front-to-back (`acc += a*(1-acc)`) starting at the element's own background, and read `backgroundImage` or a gradient band resolves to transparent. The difference is ~0.45 of a ratio point and it decides AA calls.

### Product identity (0179–0181, arc closed 2026-08-21)

- **FOUR LAYERS, one pointer changed.** `menu_items` → `items` (prep registry) → **`products`** → `vendor_items` (per-vendor packs, prices, weights, pars). A product is the raw identity a recipe means ("HAM"); member SKUs attach via `vendor_items.product_id`. **A SKU with `product_id` NULL is an implicit SINGLETON** — resolution is trivially itself — which is why ~95% of the catalog has no product row and needed no data migration. Products exist only where PLURALITY does. Retirement is `active = false`; append-only, no DELETE path.
- **RESOLUTION HAPPENS ONCE, AT GRAPH BUILD, AND IT IS PURE.** `resolveProductMember` (`lib/products-shared.ts`) is THE ladder: **⓪ the PRODUCT itself is retired → honest `unresolved`** ① the primary flagged for this location, **if active** ② else the most-recently-**received** active member ③ else any active member (`skuId` ascending — a stable, not arbitrary, pick) ④ else honest `unresolved`. A flagged primary that is inactive or not a member **falls through; it never fails the product** — that is the vendor-down behavior the whole layer exists for. `loadRecipeGraph` runs it and hands every consumer a resolved SKU id, so costing, depletion, production, counts and ordering stay SKU-keyed and gain failover for free. **Never resolve a product a second time in a consumer** — a second resolver is a second opinion about which vendor a product means, which is exactly what this layer was built to end. `product_primaries` uses the `location_id NULL = global` house idiom, and membership is DB-proven by a composite FK, never app-trusted.
- **RETIREMENT REFUSES, AND THE RECIPE GOES LOUD** (Juan's ruling A+, 2026-08-21; sim P1-9). `products.active = false` is Juan declaring a fact about the kitchen — we do not buy this identity any more — and rung ⓪ honours it ahead of every member check, because a retired product's members are normally still active rows and falling through would overrule the declaration with an inference. `ProductResolution.reason` names the cause (`retired_product` vs `no_active_member`): the STATUS stays the single `unresolved` everywhere downstream — costing board, depletion, production, ordering — but the drawer, the readiness lane and the audit row say WHICH errand fixes it: a recipe edit, not a trip to the SKU catalog. **RECIPE EDITING ≠ RETIREMENT.** Swapping a product out of one recipe is just recipe editing and touches none of this. **Retirement means "we stop buying this entirely", which is an ORDERING-layer decision** (Juan, 2026-08-21) — so **the par pass SUPPRESSES par'd member SKUs of a retired product**: they drop from suggestions, they are never rescued by the vendor-down failover (rescuing would re-order the product we stopped buying), and they surface in the walk's warn lane as `productRetired` ("discontinued — par suppressed"), loud and never silent. **Pars are SUPPRESSED, never MUTATED** — the `weekday_par`/`weekend_par` columns are untouched, so bringing the product back restores the exact prior walk with no par re-entry. Pars are downstream of demand (they exist *because* recipes create demand), so a retired product's pars are stale by definition.
- **PAR ADVISORIES ARE CAUSE-ATTRIBUTED, AND NEVER NUMERIC** (Juan, 2026-08-21: *"the pars should be loud about why they need to be tuned down when demand lessens… the system recognizes what's going on before the human does"*). `parReviewAdvisory` (`lib/location-sku-shared.ts`) nudges a par only on a **CHANGE** — a discontinued product, or a recipe that stopped using the SKU — and it NAMES the recipe. **A STATE IS NEVER A TRIGGER:** "has no active recipe" fires nothing, because live-verified 2026-08-21 that state covers 57 inventory-only SKUs plus resale goods that had no consumer recipe (AMENDED 2026-08-28, seed 31: the beverage cohort NOW carries 1:1 consumer recipes so drinks deplete and Dynamic Pars can speak for them — the LAW is unchanged, a state still never triggers; the census behind the ~73-of-77 figure is what moved) — an advisory on it would cry wolf on ~73 of its first 77 rows, and a lane that cries wolf gets scrolled past. **Suggesting a par NUMBER is out of scope and reserved for the Dynamic Pars arc**: that needs demand-rate math over a velocity window, and a figure invented from one removed recipe line would be exactly the confident-number-with-nothing-behind-it the costing board's `unweighed` status exists to refuse. **`loadProductIndex` deliberately does NOT `.eq("active", true)` the products select**: a filtered-away row poisons with no name, and `productBySku` + the member list are still true facts a count sheet uses to label twins. The active filter lands *inside* the pure resolver, which is the only place that can name itself. Same historical-replay boundary #272 drew for inactive recipes: nothing replays history through this loader, and ledger rows keyed by `vendor_items.id` are never re-resolved. **Retiring NEVER hard-blocks** — `/admin/products` warns "N recipes still pin this" (named when few) and proceeds; the write-time guard (`assertProductLineIsValid`) only stops a NEW line being authored into that state. Readiness gains two codes: `retired_product` (RED, a real refusal) and `retired_sku` (AMBER RIDER — a deactivated SKU pin gets **loudness only**, because `loadSkuPack` still includes inactive SKUs for historical replay and flipping that moves live numbers; it is its own decision).
- **A PRODUCT OWNS `unit_oz`, NOT A PACK.** A product-pinned recipe line may be denominated ONLY in a **measure-registry** unit; `productInputBasis` returns `packChain`/`packFormat`/`eachContainerLabel` all null so `ozForRecipeInput` lands on the registry. "1 case" of one vendor's ham is not "1 case" of another's, and a product pin has no honest way to choose — so it is not offered the choice. A count-denominated line resolves through `products.unit_oz`, member-independent by construction; that is what makes a member flip cost the same ounces. `addRecipeInput` rejects a pack-label unit at write time by name. NULL `unit_oz` refuses (poisons to `unresolved`) rather than guessing.
- **FIFO IS A READ-TIME ATTRIBUTION. The depletion ledgers are never re-keyed.** `toast_daily_depletion.direct_oz` keeps its exact meaning, `flattened_oz` is still never summed into drift, and **the double-count law is not in play here**. FIFO runs in the pure core over lots assembled from `vendor_delivery_items` (`created_at` is the lot instant), oldest-first with a `lotId` tiebreak; what a lot cannot explain is **reported as unattributed, never smeared and never dropped**. The mirrored false SHORT/OVER pair is cured by the **rollup** — twins net at product grain — not by touching a ledger row.
- **A PRODUCT-LEVEL COUNT WRITES ORDINARY PER-SKU LINES.** `sku_count_lines` gains no product grain; C-mode resolves oz through the primary's basis, allocates it across member lots **newest-back** (the freshest lots are what the counter is looking at), and writes one line per member with `allocated_from_product_id` set — NULL means counted directly. **Every active member gets a line, including a zero one:** a product count re-anchors the WHOLE product, and that zero is a *measured* zero ("none of it is Baldor's"), categorically different from the F3 refusal of an operator typing 0. **A COUNT IS GROUND TRUTH AND THEORY YIELDS TO IT** — oz the ledger cannot place is attributed to the resolved primary with an advisory reason code (`no_lot_history` when there are no lots at all; `count_exceeds_lots` when there are and they fall short — never conflate them), never refused. **One product line per event**: two lines for one product breaks the council-L5 disjointness the anchor sum rests on. On-hand is TWO GRAINS: the per-SKU ledgers stay the truth, the product grain is their sum, `totalOz` is non-null only when every member resolved, and `knownOz` is a lower bound that must never render where a total belongs.

### Dynamic pars (0182–0183, arc closed 2026-08-28)

- **`resolvePar` IS THREE LANES, AND A HUMAN ALWAYS WINS.** `human ?? auto ?? global` (`lib/location-sku-shared.ts`) — the per-location human override, then the machine's standing value, then the global `vendor_items` par. **The machine's lane is never the top rung and never the bottom one**: it may not overrule a manager, and it may not become the number a shop that never opted in inherits. A `location_sku_settings` row with no human par and no auto par reduces to exactly today's behaviour, which is what made both migrations byte-identical on the walker before they were applied. **Auto values SELF-INVALIDATE on a global par change** (r2-6): the machine persists the `auto_*_baseline_par` it computed against, and a baseline that no longer matches the global par retires the auto value at READ time — no sweeper, no staleness window.
- **THE MACHINE WRITES ONLY ITS OWN COLUMNS, AND ONLY THROUGH THE ONE AUTHORITY.** `parWriteColumns` (`lib/dynamic-pars-shared.ts`) is the single place that decides what ANY par write does to the machine lane, the baseline and the pin — the admin overlay editor, the walker's one-tap accept, a revert, and the nightly engine all resolve their column patch there. It is not "one function performs every write" (the admin path also owns `active_override` and its own insert-vs-update dance); it is **one place decides**, because a second opinion about that is how the machine ends up masquerading as an operator. **The bypass is closed STRUCTURALLY, not by validation:** for `kind: "admin"` every value the function puts in `autoLane` is NULL, for every input — no operator payload reaches a non-null auto write, which holds even if the admin route's field list changes. **Per-slot, never per-row:** only the named day-class's columns appear, so a weekday move cannot stamp the weekend slot's history. **Time enters as a parameter** — a `revert` with no `appliedAt` THROWS; a `new Date()` fallback would break the module's purity promise and a silent `?? null` would DROP the pin, on the one column whose whole job is to stand.
- **THE BAND SPEAKS IN PAR STEPS, AND PARS ≤ 3 STEPS ARE MANUAL-ONLY.** Magnitude is `max(1 step, 25% of par)`, and **the cap clamps AFTER rounding** — the band tests the ROUNDED delta, which is what structurally closes the hole where a raw Δ2.5 passes a ≤2.5 cap and only then rounds to a 30% move. **Beyond the band is a SUGGESTION AT THE FULL, UN-CLIPPED TARGET**, never a partial auto-move toward a target the machine may not reach: "nothing beyond the band ever moves itself", and the manager sees the honest number. Below `MIN_STEPS_FOR_AUTO` (4) the band has no resolution — ±1 step is the largest relative swing exactly there — so the suggestion renders labelled `below_band_resolution` and the auto tier is unreachable. At CO that is 108 of 141 pars, and saying so is the honest answer, not a bug. A **one-step suggestion deadband** damps the wobble a manager learns to ignore; its stated cost is that a permanent one-step drift renders stale until it reaches two.
- **THE BUDGET IS CONSUMED BY AUTO-WRITES AND REVERTS. ACCEPTS ARE FREE.** One non-manual par write per `(sku, location, day-class)` per rolling 7 days. A revert is a non-manual-origin write and pays, because the budget is what stops a revert war; an ACCEPT never pays, because **the incentive must not punish engagement**. The budget is a COUNT OVER THE RECOMPUTABLE LEDGER, not a stored counter — which makes shadow a genuine longitudinal simulation and a re-invoked nightly run idempotent (it counts `applied` always, `would_apply` only from EARLIER runs). A within-band delta on a spent budget gets its OWN cause, `budget_spent`, and **still renders its number** — without it the row is neither auto nor suggestion and reads as a silently stale par.
- **A PIN IS CLEARED ONLY BY A DIRECT HUMAN EDIT AT THE SAME SLOT.** A revert SETS the pin; **the act that sets a pin never clears it**. A global par edit invalidates the auto VALUE but the pin stands. The pin stops the MACHINE, not the conversation: the suggestion keeps rendering under `pinned`, only the unilateral write is off. A revert **refuses with `409 nothing_to_revert` unless an `applied` row really exists** — otherwise a revert in shadow would pin a slot the machine never moved, punishing a future auto-move for something that never happened.
- **THE COVERAGE HORIZON ENDS AT THE SECOND-NEXT DELIVERY, AND IT IS SELECTED AT READ TIME.** Order-up-to-par is a base-stock policy: the target must cover **lead time PLUS the review interval**, because the order placed at this walk IS the next truck. Covering only to the next delivery under-orders by a whole inter-delivery gap (~50% on the main path). Covered days are exactly `{ d : walkDate < d < coverThrough }` — the walk is after service, the delivery lands before it. **The nightly persists the demand TERMS; the walk re-runs only the trivial halves (`computeCoverage` + `applyGuardStack`) over them against the horizon at the REAL instant** — so a 9:58 and a 10:02 walk render different, both-correct numbers from ONE ledger row, for one indexed query and no re-derivation. That is a pure SELECTION, not a mutation: **the write-on-read law forbids mutations on a read path, not selection.** Two riders: the read must load BOTH day-classes paired on `run_date` (a Thursday horizon reaches into Friday and needs the weekend rate; halves from different nights are a partially-written ledger, so honest-null instead), and **the walk-time tier is never richer than the ledger's** — a read path may not acquire an auto verdict it cannot see the guards for. Rhythm is per-location order→delivery **PAIRS** and **explicitly non-inheriting** (the deadline is usually one phone system; the trucks are not — so `vendor_cutoffs` may be shared across shops and rhythms may not). `nextDeliveryAfter` **never reuses `governingCutoffTime`**, whose earliest-of-today tiebreak is a DISPLAY rule; `cutoffForOrderDay` is the dow-parameterised twin. Legacy `vendors.delivery_days` is never read here. **BOTH BOUNDS ARE SELECTED IN ARRIVAL ORDER, NEVER IN ORDER-DATE SPACE** (Juan, 2026-08-31: *"we def need to build for mixed lead times… no cut corners"*). A shelf is replenished when a TRUCK LANDS, so `upcomingDeliveries` enumerates the catchable (order, delivery) pairs once and `coverageWindow` re-sorts them by arrival: `nextDeliveryDate` is the earliest arrival, `coverThroughDate` the earliest arrival **strictly after** it — which makes the old inversion structurally impossible and collapses two same-day trucks into one replenishment instant. With UNEQUAL leads on one vendor the orders CROSS in transit (Mon at lead 3 lands Thursday; Tuesday's lead-1 order lands Wednesday and overtakes it), and order-space selection returned `coverThrough` EARLIER than `nextDelivery` with a covered set one day short. **`orderDateEt` stays ORDER space** — it is the deadline the walk is working to, not a truck, and under crossing it can be the order of a *later* arrival. Equal leads make arrival order and order order the SAME order, so this is a byte-identical no-op on CO's live rhythm (50 pairs, every one lead 1, prod-probed 2026-08-31) — pinned by a differential regression against the pre-ruling selection over the uniform-lead fixture matrix, which is the test any future change to this selection must still pass.
- **THE REASON LANE IS THE PRODUCT, AND A SILENT PAR ALWAYS NAMES ITS ERRAND.** v1 speaks for ~14 rows of 282 and NAMES the errand for the rest; phase success is measured in reason-lane completeness, never suggestion volume. **A phase that ships 0 suggestions and a complete, accurate, i18n'd errand list is a success; one that ships 40 by loosening a gate is a failure.** A silenced par is still a full ledger WRITE. **The vocabulary is CLOSED and the COMPILER enforces it** — `ParReasonCode` is the only spelling of a reason anywhere in the arc, a bare string is never a reason code, and `par_auto_moves.reason_code` deliberately carries **no DB CHECK** (the same posture `audit_log` takes with `AuditAction`: closed on the write side, so a DDL enum would only force a migration per new cause). **First cause wins and the ORDER is the point** — `inventory_only` ranks first because 114 of CO's rows are packaging and an errand for them would put 114 false chores at the top of Juan's list on day one. The lane renders in the **AGGREGATE** (one line + a default-collapsed per-cause errand list), never as a per-row badge while ~94% of rows are silent; `shouldBadgeSilencePerRow` ships now, returns false now, and **lights itself** when silence becomes the minority — no flag, no future PR. Three tiers, and **no "other" bucket**: errands in the weight→rhythm→cushion critical-path order · remaining faults · the two NOT-A-FAULT causes last. A cause attributed wrongly is an ERRAND aimed wrongly, which is why a 0-oz order unit is `no_weight_basis` and not `thin_history`.
- **VELOCITY IS A BOUNDED DIMENSIONLESS RATIO AND CAN NEVER ENTER AN OZ SUM.** It is a RESIDUAL above the SKU's own day-class trend, never a level — recent sales are already inside the trailing window, so a level term double-counts the very days it is meant to lead. Two gates, both required: time (a run of same-signed residuals past the deadband) AND volume (the SKU actually moves) — a sustained 3-item/day +200% passes time and fails volume, and tripling a par on three items a day is how a par teaches a manager to ignore pars. Suggestion-lane only in v1. **Suspect (catering-shaped) days are excluded via a DAY-GRAIN marker, never a lane change** — `toast_daily_sales_signals` rides inside `materializeDailyDepletion`'s existing idempotent day scope.
- **THE EVENT (CATERING) LAYER IS NAMED AND NEVER SUMMED.** The walker shows a name and a date; it does not net catering out of demand. `productions` cannot say which quote it served, so netting would be a guess — and the stated limitation (a catering-driven prep counted once, as ordinary demand) is recorded rather than papered over. The quote-link is the filed enabler that upgrades this from advisory to arithmetic.
- **THE DOUBLE-COUNT LAW IS NOT IN PLAY, AND `direct_oz` WAS NOT TOUCHED.** Consumed oz = `production_inputs.input_oz` + `toast_daily_depletion.direct_oz`, **never `flattened_oz`** — the same two lanes `loadSkuUsageRank` and the counts drift term already use. This arc reads flattened oz for exactly ONE purpose — detecting that a SKU's demand is PREP-MEDIATED, i.e. that its true consumption lives in a lane that is currently dark — and never sums it into anything. A half-seen base is silently LOW, which is worse than null, so a prep-mediated SKU with no production capture is advisory-null with its cause named. **Rates are computed at PRODUCT grain, per date** (a primary flip must not read as demand collapse), through the one shipped rollup — never a second one — and **the auto value is homed on the DESIGNATED primary's slot, never the transient carrier**, so a tuned par survives the vendor's restore.
- **Three exclusions from the base, each counted separately and each for a different reason:** before `lane_start_at` (the lane did not exist — structural zeros, not measurements) · full-gap days, where NEITHER oracle fired (`toast_sales_events` is the register-ran oracle: the shop's DATA is missing, not its demand — **exclude the day, never null the window**) · and nothing else, because **a day the register ran and this SKU did not move is a TRUE ZERO** and belongs in both the numerator and the denominator. **A percentage on a mean is not a service level:** until the statistical cushion has variance-worthy history, a suggestion may never fall below the **observed p90 peak** over the horizon length (max below 5 runs — with 4 runs a "p90" is a max wearing a costume). Expect the floor to lead the trailing base during a demand step; that is the floor doing its job, and `tests/dynamic-pars-scenarios.test.ts` pins it.
- **Authorization: the par floor is level 7 and the location bind lives IN THE LIB.** 7 is what "GM" means here (`gm` = 7; level 6 is AGM / catering_mgr / prep_mgr **and social_media_mgr**) and is exactly today's only par-write floor. Suggestions RENDER at `PAR_PASS_MIN` (4) for transparency; accept/dismiss/revert take **no step-up** — `/ordering` is an operational 6 AM surface and a password prompt there is the affordance's death, and the blast radius is one slot, one value, computed by the system and rendered to the actor before they tapped. The admin overlay route keeps its Tier-A step-up untouched. **Level 7 is NOT all-locations** (`lockLocationContext` grants that at 9), so the bind runs inside `writeParFromSuggestion` / `dismissSuggestion` — before the arbiter claim and before any I/O — with the route's bind kept as the outer layer: defence in depth, not redundancy.
- **One suggestion generation, one human verdict, ARBITRATED BY A UNIQUE INDEX — and the arbiter runs BEFORE the mutation.** `par_suggestion_actions` `UNIQUE (location, sku, day_class, generation_id)` IS the guard; the loser of a double-tap gets `23505` mapped to `409 suggestion_already_actioned`. Claim first, then write: the other order guards nothing (two taps both land their UPDATE and one is then told nothing happened). The stated trade-off — a consumed generation with an unmoved par — is the RIGHT failure, because the reverse orphan is a kitchen change with no accountability record. **The route posts an IDENTITY, never a value:** the par written is re-derived server-side at the request's own walk instant, and a stale generation is a 409. **The ramp counts DISTINCT GENERATIONS**, structurally, so nightly re-renders can never inflate it. **Graduation widens the TRIGGER, never the WRITE SET** — a graduated location still auto-writes only lane-lit SKUs — and its count anchor requires `allocated_from_product_id IS NULL`, because a product-level count allocates a line to every member and would otherwise anchor a whole product at once.
- **`par_auto_moves` is append-only with ONE immutable class.** The nightly recompute deletes `(run_date, location)` **AND `outcome <> 'applied'`**: a `would_apply` / `suppressed` / `advisory_null` row is a re-derivable opinion, an `applied` row is the record of a real par write and is never deleted and never updated. **The ledger insert is NOT fail-open like `audit()`** — a failed ledger write must throw so the run is retried, and the cron's per-location try/catch contains it. Audit volume is **ONE run-level row per (location, night)**; 282 per-SKU rows a night would be ~21× the entire audit log annually, so the night's whole story rides in that row's reason histogram. The cron's depletion gate is the materialize loop's **own result OR `watermark >= businessDate`** — never strict equality, which is wrong in both directions (a zero-consumption day leaves the watermark on yesterday; a `?date=` backfill runs ahead of it) and whose false skip WRITES, so it is data loss rather than a no-op.

### Engineering doctrine

- **Verify against operational artifacts, not generic priors.** CO has zero walk-ins and zero freezers; it has eight under-station fridges. The existing templates, paper checklists, schema, and Juan's floor knowledge are ground truth; training-data "what a restaurant has" is not. Multi-source verification (Juan's knowledge / DB queries / paper artifacts / code pre-read / rendered smoke) before locking operational structure — each source class catches gaps the others miss.
- **"Preserved from prior" must be re-verified against any amendment that changed its operational assumptions** (the C.54 §9 production wedge). When an amendment lands, audit every carried-forward branch for invalidated assumptions.
- **Before building a reader, confirm the writer runs in prod** — a correct-shaped consumer of a contract nobody produces is dead code that looks finished.
- **The codebase has usually already built the thing** — read for existing scaffolding/patterns before scoping anything as greenfield (three-plus confirmed repetitions).
- **Read surfaces over new workflows:** new capability defaults to a computed read over existing capture artifacts; new workflows only when the data genuinely doesn't exist — and then extend an existing artifact first.
- **Wire-shape coupling sets commit boundaries:** form/route/RPC/migration/type changes that are type-coupled ship together; splitting at conversational boundaries produces broken intermediate states.
- **Validation iterates the source of truth** (templateItems, schema, config), never operator-state-only structures (rawValues, dirty sets) — the latter are a subset.
- **Shared-type changes get a consumer grep before commit** (`grep -rE "<TypeName>\b"`); role-gate changes get the 3-layer sweep (lib + RLS + UI, both directions of the comparison).
- **Ship-complete:** partial scope must clear the architectural-deferral bar (different module/data model/tempo, deserving its own design). "Translate it later" and its cousins never clear the bar.
- **Smoke tests are architectural finders:** when a first-shift report feels off, surface the architectural read BEFORE bug-fixing. `router.refresh()` does NOT reset client `useState`; prop-driven client-state resets use the during-render prev-compare pattern, not effects; irreversible affordances gate on server-authoritative status, never spinner state. Map observed→expected before calling a smoke red — refusal-to-resubmit is the fix working.
- **Operational voice varies by audience:** capture surfaces use the actor's technical wording; notification/consume surfaces use operational shorthand; both registers survive translation.
