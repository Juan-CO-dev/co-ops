# Landing measurement — chunk A

The browser Pixel, CAPI enhancement and independent direct-order counter have separate activation switches. All are host gated and honor first-party consent, DNT and GPC. Nothing here establishes purchases or unique people. The default configuration sends no Meta requests and makes no counter writes.

## Event contract

PageView and ViewContent are browser-only. Lead is the catering inquiry. OrderClick and CateringClick are custom events, using Pixel trackCustom. A real action generates one UUID shared by browser eventID and server event_id; a retry retains the same name/ID. The counter never retries and never receives the UUID. Source URLs contain only the configured landing HTTPS origin and the public document path, with no query or hash. The only initial ad code is `subsim-photo`; unknown counter codes collapse to `unattributed`. Direct shop keys are `capitol-hill` and `dupont`. No offer is activated by an ad code.

## Server boundary and activation

Landing section ViewContent requires at least 50% visibility for a continuous 1,000 ms while the document is visible, with consent and privacy-signal gates unchanged. Normally the observed target is the section's content wrapper. The `crave` section is the explicit exception: its long native-scroll stage observes the contained `#crave-title` heading instead, so the event remains reachable on short screens. Leaving the threshold or hiding the document cancels the dwell; it is still emitted at most once per section per page visit. This does not add a new event or change the event payload.

Both POST routes independently verify authoritative Host, forwarded-host agreement, exact configured HTTPS Origin and same authority. Missing/null/foreign Origin is refused even when dormant. The accepted first-party `landing_consent` preference is required, conflicting duplicate cookies are refused, and DNT=1 / Sec-GPC=1 override consent. CAPI also requires consent in the bounded JSON payload. Body limits are 4096 bytes for events and 512 for the counter, including bodies without Content-Length, with a two-second body-read limit. Unknown fields are rejected. No CORS wildcard is provided.

CAPI requires `LANDING_CAPI_ENABLED=true`, numeric `META_PIXEL_ID`, server-only `META_CAPI_ACCESS_TOKEN`, `META_GRAPH_API_VERSION=v25.0`, `LANDING_META_UA_APPROVED=true`, legitimate consented fbc/fbp matching data and the WAF evidence below. Missing matching data yields a no-op 204, never a claim of delivery. No client IP is collected. User agent and advertising identifiers are personal data: Juan must approve their disclosure before activation. A `META_TEST_EVENT_CODE` is allowed only for `VERCEL_ENV=preview` or `development`, or when `VERCEL_ENV` is unset and `NODE_ENV` is not production. All other combinations are refused, including production builds outside Vercel. Preview test codes remain server-only. The Graph request has a two-second timeout, uses an Authorization header (never a credential in its URL), refuses redirects, and returns only an empty status. Upstream failures return 503 without retry, response reflection or logs. CAPI never imports the Supabase writer or writes an audit row.

The independent counter requires `LANDING_COUNTER_ENABLED=true` only after migration 0273 is reviewed/applied by CC/Juan. This implementation authors the file only and never applies it. Its RPC computes the UTC day in PostgreSQL and atomically increments one bigint per day/store/ad. The table contains exactly those four fields. Anon/authenticated have no table or RPC privileges and deny-all RLS; service_role has SELECT plus RPC execution, no direct insert/update/delete/truncate. Unknown stores and oversized/null ad values are refused at the RPC too. There is no decrement, reset, backdate or deletion API.

## WAF verification is deployment work

`LANDING_WAF_STATE` is dormant (default), active, refused or unavailable. Active additionally requires operator-owned `LANDING_WAF_VERIFIED_AT` (YYYY-MM-DD) and `LANDING_WAF_RULE_IDS`. These env values are an attestation of external verification, not proof that dashboard rules exist and not an in-process rate limiter. No incoming client header can enable or bypass protection. `refused` produces 429; an active-protection outage recorded as `unavailable` produces 503. Missing or unverified evidence keeps CAPI dormant. The independent approximate counter can run without WAF and is therefore susceptible to anonymous inflation; it is not billing/conversion truth.

On Vercel Pro, use two published rules scoped to the landing deployment:

- **Rule A (WAF, before app code):** exact landing hosts, POST, path in {/api/landing/events, /api/landing/order-click}; fixed 60-second window, 30 requests per IP, action 429. Pro dashboard rate-limit keys are IP or JA4; they cannot express an aggregate key.
- **Rule B (SDK, before registry/transport/counter I/O):** its ONLY condition is rate-limit ID `landing-aggregate`, fixed 60-second window, limit 600. Do not add rule A's host/path conditions. After cheap local gates, both handlers call `@vercel/firewall` with separate constant keys: `landing-capi` for events and `landing-counter` for order-click. Each gets **600/min per route, per region**, so counter traffic cannot exhaust the CAPI bucket. CAPI checks aggregate refusal/unavailability and skipped-protection dormancy before resolving the ad registry, then sends to Graph; the counter checks aggregate before incrementing. The SDK timeout is 1,000 ms. Refusal returns 429; an exception, timeout, missing rule, missing Host or invalid switch returns 503. With `sdk`, passed `NODE_ENV` must equal `production`; otherwise protection is unavailable (503), because the SDK itself silently allows non-production runtimes.

Vercel counters provide **600/min per route, per region**, not a single worldwide ceiling. Record the deployment regions with verification evidence. `LANDING_AGGREGATE_LIMIT=sdk` is required for production CAPI. Unset or `off` skips aggregate protection; CAPI may send after the other gates only when `VERCEL_ENV` is `preview` or `development`, or when `VERCEL_ENV` is unset AND `NODE_ENV` is not `production`. Every other environment combination stays dormant (204, no registry read or send), including empty or unknown `VERCEL_ENV`. Preview Test Events initially run with it `off`. The independent counter continues with the switch unset or `off`, by design.

Before CAPI activation E4 must record plan entitlement, dated rule IDs/config, host/path scopes, cross-instance concurrent/burst enforcement for both rules, 429 behavior, spoof resistance, actual Vercel x-real-ip/XFF behavior, provider retention and disclosure. No app IP logs. Dashboard removal/outage cannot be inferred from a request header; the operator must disable CAPI / mark protection unavailable when protection is not verified. Under E4 provider retention and disclosure, record that the SDK forwards a copy of all incoming request headers as `x-rr-*` to Vercel's rate-limit endpoint, including cookies (`landing_consent`, `_fbp`/`_fbc`), user agent, x-real-ip and XFF. Vercel is the existing processor; the app logs none of these headers.
